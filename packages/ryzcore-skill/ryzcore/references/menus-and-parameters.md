# Master tables, parameter maintenance, and menus

## Naming rules

```text
rf_*      reference/master/parameter data (configuration, lookups, templates)
tb_*      transaction/configuration tables
um_*      user management tables
enum_*    enums
temp_*_pending  maker-checker staging for CRUD features
```

- A master/reference table is named `rf_<domain>` in snake_case.
- Do not invent a `tb_` name for master data.
- Master tables default to a `varchar(50)` string id (uppercase code), not
  `uniqueidentifier`; a matching FK column in another table uses the same type
  and values. Existing tables with an identity key (for example
  `rf_email_provider`) keep their identity key.
- Do not reuse or rename existing legacy table names (`um_*`, `rf_*`,
  `tb_parameter_system*`, `proc_seq`); only project/database/namespace names
  are parameterized.

## Master table recipe: rf_* as parameter maintenance

When the task is "buat table master", "tambah master data", or a new
configuration/reference table, the expected result is a table named `rf_*`
whose UI is generated by parameter maintenance (maker + approval), not a
dedicated CRUD page or menu.

1. **Create the table and entity**
   - Entity file: `Domain/Entities/rf_<name>.cs`, one public class per file,
     lowercase class name matching the table.
   - Inherit `BaseEntity` so the standard columns exist: `status_approval`,
     `is_active`, `is_deleted`, `is_locked`, `is_default`, `approved_by`,
     `approved_date`, `approval_type_id`, `created_*`, `modified_*`,
     `deleted_*`. Legacy tables such as `rf_email_provider` use
     `BaseAuditEntity`; the approval procedure tolerates missing approval
     columns, but new master tables use `BaseEntity`.
   - Add the table mapping and a new EF migration; never edit an applied
     migration.

2. **Register the card in `ParameterSeeder.Cards`**
   - Add `(table_name, description, icon)` to the `Cards` array in
     `Infrastructure/Data/ParameterSeeder.cs`.
   - The maker URL is generated as
     `/dashboard/maintenance/parameter-system/maker/{table_name}` and the
     approval URL as
     `/dashboard/maintenance/parameter-system/approval/{table_name}`.
   - Special pages keep a custom maker URL
     (for example `tb_screen_menu` -> `/dashboard/maintenance/screen-menu-editor`).

3. **Register the field metadata in `ParameterSeeder.SeedFieldsAsync`**
   - Add `AddFieldsAsync(context, "rf_<name>", cancellationToken, new[] { ... })`.
   - Use the existing `Field(name, label, type, key, mandatory, order, reff)`
     helper. Supported `field_type` values: `text`, `textarea`, `html`,
     `password`, `bit`, `list`, `number`.
   - `list` fields use `reff` with a SQL query returning `value` and `text`
     columns, for example
     `select def_code as value, def_name as text from rf_default_value where is_active = 1`.
   - The metadata drives the maker edit dialog and the approval diff display.

4. **Add the table to the engine allowlist**
   - `ParameterEngineService.AllowedTables` in
     `Infrastructure/Services/ParameterEngineService.cs`.
   - The allowlist in `database/stored-procedures/usp_parameter_sytem_save.sql`
     and `usp_parameter_sytem_approval.sql`.
   - Keep all three lists in sync with `ParameterSeeder.Cards`.

5. **Do not create a menu, page, controller, or service for it**
   - Parameter maintenance renders the maker and approval card automatically
     from `tb_parameter_system` + `tb_parameter_system_detail`.
   - Dedicated menu entries are only for the parameter maintenance pages
     themselves (`MNT-PARAM-MKR`, `MNT-PARAM-APR`) which already exist.
   - Do not add an `um_menu` entry for a new `rf_*` table.

6. **Understand the approval flow**
   - Maker create/update/delete writes to `tb_parameter_sytem_temporary` and
     `tb_parameter_sytem_temporary_detail`; it does not change the real table.
   - Approval applies the staged values through the stored procedure:
     insert/update/delete, sets `status_approval = 4`, `approved_by`,
     `approved_date`, and requested audit fields.
   - Reject removes the staging rows.
   - Approval uses `field_key = 1` metadata to locate the row; a table without
     key metadata throws `51012`.

7. **Seeder behavior**
   - `SeedCardsAsync` checks per card, so a new card is inserted on the next
     API start even in an existing database.
   - `AddFieldsAsync` skips a table entirely when it already has any field
     metadata. For an existing database, insert the new
     `tb_parameter_system_detail` rows manually or through a migration; editing
     the seeder alone will not update existing installations.

8. **Verify**
   - API starts with `Seed:Enabled` (or `--seed-only`).
   - Parameter Maintenance shows the new card in both Maker and Approval.
   - Create/edit/delete in maker produces a pending row; approval applies it to
     the real table; reject removes the pending row.
   - No `tb_audit_trail` rows are written manually; audit comes from the
     centralized DbContext save path for normal CRUD, while parameter
     maker/approval is handled by the engine and parameter stored procedures.

## Menu creation

Menus are database-driven. Never hardcode menu items into the Web or MAUI
layout.

### Menu tables

```text
um_menu            menu identity, url, parent, icon, order, component type, level
um_group_menu      maps a menu to a group (admin group code "00")
enum_menu_icon     icon catalog (Font Awesome + Material alternate names)
tb_screen_menu     dynamic screen/list definition
tb_screen_menu_child  dynamic modal/URL action definition
tb_report_set      dynamic report/report list definition
```

Levels: `A` = top group, `B` = menu group, `D` = leaf page. Link children
through `menu_unique_parent` (the parent's `menu_unique`).

### Static Razor page menu

1. Add the page under `Shared/Pages/...`.
2. Add a menu row to `MenuSeeder.Menus` with:
   - `menu_unique` (for example `MNT-USER-LST`);
   - `menu_url` (for example `/dashboard/maintenance/user-list`);
   - `parent_level_id = "D"` and `menu_unique_parent`;
   - `component_type` = full type name
     (`__PROJECT__.Shared.Pages.Maintenance.UserList, __PROJECT__.Shared`)
     for static components;
   - icon and order.
3. `MenuSeeder` inserts `um_menu` rows and maps all menus to the administrator
   group (`"00"`) through `um_group_menu`.
4. Existing databases: add the rows through Menu Maintenance or insert into
   `um_menu` + `um_group_menu`; seeding only runs the full set when `MNT` does
   not exist yet.

### Dynamic screen menu

1. Create `tb_screen_menu` row (`id` `SM-*`) with `field_filter`,
   `query_load`, `query_load_param`, `query_delete`, button flags, and
   `screen_menu_child_id` when a modal is needed.
2. Create `tb_screen_menu_child` (`SMC-*`) for modal/URL actions with
   `modal_field`, `modal_detail_field_query`, `modal_save_process_query`, or
   `url_action` and their param arrays.
3. Add the menu with `menu_url` = screen id (for example `SM-DEFAULT-VALUE`)
   and `component_type = "DynamicScreen"`.
4. `Screen Menu` itself is edited through the Screen Menu Editor page, which is
   registered as a parameter card with a custom maker URL.
5. Dynamic report menus use `tb_report_set` and
   `rf_group_access_report_set` for access.

### Parameter cards are not menus

A new `rf_*` master table does not get an `um_menu` row. Its maker and approval
screens appear inside Parameter Maintenance because of the
`tb_parameter_system` card registration above.

## Data-menu rule

Data menus stay database-driven. Never hardcode menu items into the sidebar,
MAUI layout, or a Razor page; add the database rows or the seeder entry instead.
